# Browser compatibility: Safari (macOS) and Brave/Chrome (Windows)

Status: research output for `versions/v0.1.0/01-session-contract/02-validate-browser-capabilities.md`. Gathered 2026-10-13. **Nothing here has been run on a real browser yet**; section 4 lists what must be verified.

Evidence tags: **[BCD]** MDN browser-compat-data (raw JSON, `main`), **[MDN]** MDN content, **[AD]** Apple developer documentation, **[RN]** Safari release notes, **[WK]** WebKit source on `main` (current code, not tied to a shipped Safari version; Safari's own app-side delegate code is closed), **[CD]** Chrome developer docs. Chrome docs were read through a summarizing fetch tool, so quote-level precision is not guaranteed. URLs are in "Sources" at the end. BCD has no Brave column; Brave is treated as Chromium (current Brave 1.97.56 ships Chromium 155 per its changelog).

## 1. Capability matrix

"Min" is the first version with the feature. Safari values below 15.4 are moot because MV3 needs 15.4.

## 2. Safari behavioral differences that affect us

1. **Background suspension.** Non-persistent background is unloaded 30 s after the last activity; open ports keep it for 2 min; a pending permission prompt or an open inspector blocks unload [WK WebExtensionContext.cpp/.mm]. Apple tells non-persistent extensions to register listeners at top level, keep state in `storage`, and use `alarms` instead of `setTimeout` [AD optimizing]. Safari persists the registered event-listener set so it can wake the background for events [WK], which only works if listeners are registered synchronously at top level. A bug where background pages stopped responding after about 30 s was fixed in 17.6 [RN 17.6] (introduction version not stated), a reason to set the minimum at 18.x.
2. **Alarms.** Safari alarm timers live in memory and wake the background when they fire [WK]. They are not persisted by anything found in the code, so assume they die with Safari and never fire while Safari is not running. Chrome alarms persist across restarts (default) but also do not run while the browser is closed. Consequence: on every start, run a catch-up sync and re-create the alarm. Never rely on an alarm having survived.
3. **`onRemoved` `isWindowClosing`.** Documented in MDN and Chrome. In WebKit, `didCloseWindow` closes the window's tabs with `WindowIsClosing::Yes` [WK], but whether the Safari app calls it in that order, and how quitting Safari reports tabs, is unverified. Treat `isWindowClosing` as a hint and never as the only signal for "user closed one tab".
4. **Private windows.** In WebKit a private tab or window is invisible to the extension (`extensionHasAccess` false) unless the user granted Private Browsing access [WK]. Safari 17 added per-extension Private Browsing toggles [RN 17]; granting site access in 17+ applies across profiles, private browsing and no-profile browsing [AD permissions]. Safari 17.4: extensions without private access may still open private windows [RN 17.4]. Still filter on `incognito === true` explicitly; Chrome exposes the flag.
5. **`Tab.url` visibility.** Empty string for tabs the extension has no access to [BCD][WK]. Safari's access model is per site, user-controlled: Ask / Allow / Deny, granted once, for a day, or always; the toolbar shows a badge when access is missing [AD permissions]. For tab sync the user must effectively grant "all websites", and a denied or "ask" site silently looks like an empty URL. Whether the `tabs` permission alone returns URLs in Safari is unverified (WebKit treats `tabs` as an implicit request, but the grant check goes through site permissions [WK]).
6. **Permission changes.** An update that requests more host permissions turns the extension off until the user re-enables it (16.4) [RN 16.4]. Keep the host-permission set stable across releases; use `optional_host_permissions` for the backend origin. Extensions are also enabled per Safari profile (17+) [AD running].
7. **Restore on launch and `onCreated`.** Neither Apple nor Chrome documents whether restored tabs fire `tabs.onCreated`. Unknown; see section 4. Safari also has no `webNavigation` transition data to tell a restore apart from user navigation [BCD].
8. **Misc.** Safari windows API: `windows.create` result lacked `tabs` until 18.4 [RN 18.4]. `alwaysOnTop` always false [BCD].

## 3. Packaging and local testing (Safari)

- **Tool name.** Apple now documents `xcrun safari-web-extension-packager /path/to/extension` and notes it "used to be named" `safari-web-extension-converter` [AD packaging]. Use the new name in scripts; check whether the old name still resolves on the build machine.
- **Options** (from the page): `--project-location`, `--app-name`, `--bundle-identifier`, `--swift` / `--objc`, `--macos-only`, `--ios-only`, `--copy-resources`, `--no-open`, `--no-prompt`, `--force`, `--rebuild-project`. Suggested: `xcrun safari-web-extension-packager extension/dist/safari --macos-only --swift --no-open --no-prompt --project-location safari --app-name CrossTabSync --bundle-identifier <reverse-dns>`. The packager prints unsupported manifest keys; review them [AD packaging]. By default Xcode references the source folder (no copy) [AD packaging].
- **Fast loop without Xcode** (Safari 18.4+): Safari > Settings > Developer > "Add Temporary Extension...", pick the folder or zip. Safari removes temporary extensions after 24 hours or when Safari quits [AD running][RN 18.4].
- **Unsigned build from Xcode.** Safari ignores unsigned extensions by default. Enable Safari > Settings > Advanced > "Show features for web developers" (Safari 17+; older: "Show Develop menu"), then Settings > Developer > "Allow unsigned extensions" (Safari 17+) or Develop > Allow Unsigned Extensions (16 and earlier). **The setting resets every time Safari quits** [AD running]. Then enable the extension under Settings > Extensions, grant website access, and (for private tests) enable Private Browsing.
- **Rebuild loop.** After the first install, Product > Build in Xcode refreshes the packaged extension [AD running].
- **Distribution.** Safari only runs signed extensions; options are the App Store, or a Developer ID-signed and notarized containing app for distribution outside it [AD distributing]. Safari loads Developer ID-signed, notarized extensions from **18.4** [RN 18.4]. Requires an Apple Developer Program membership [AD distributing]. For beta testers, an unsigned "Copy App" archive works if they enable unsigned extensions [AD distributing].
- **Version pinning.** `browser_specific_settings.safari.strict_min_version` can declare the minimum Safari [AD optimizing].

### Recommended targets

- **Safari 18.4 minimum** (runs on macOS 13 Ventura, 14 Sonoma, 15.4+ Sequoia per the 18.4 notes; Safari 26 supports Sequoia and Sonoma, not Ventura) [RN 18.4, 26]. Reasons: Developer ID + notarized distribution (18.4) and the Developer tab temporary install; the CORS/permission semantics for `fetch` settled in 18.4 so we build against final behavior; `storage.session` (16.4) with trusted-context default (17.1); background-unresponsive bug fixed (17.6); `tabs.create` `pinned` fix (18.3). Lowest technically possible is 15.4 (MV3) / 16.4 (`storage.session`), but several bugs above make it a poor floor. Prefer 26.2+ for testing the `onInstalled` fix, but do not require it; make `onInstalled` handlers idempotent.
- **Brave/Chromium 120 minimum** (any currently shipping Brave qualifies; check `brave://version`). Reasons: 30 s alarm floor (120), `storage.local` 10 MB (113), `storage.session` 10 MB (112), `optional_host_permissions` (102), MV3 (88).

## 4. Open questions to verify on real browsers

Answered on 2026-10-14 with Safari 27.0 / macOS 26.6.2 and Brave 1.97 (Chromium 155): closing a Safari window or quitting Safari produced no individual-close operations (the held-close rules dropped them); Safari fires `windows.onFocusChanged` on app activation; the pairing flow with `permissions.request` worked in both browsers; `tabs.create({active:false})` did not steal focus; Safari reports a pinned tab once per window with distinct ids; `storage.session` is available in both, so the new-session marker works; Brave restored its session with new tab ids and mappings re-matched by URL. Safari restores tabs lazily: restored tabs fire no `onCreated`/`onUpdated` until activated, and `tabs.query` reports their URLs, so mappings must be re-matched by URL at startup (done). Safari on this Mac restored only pinned tabs after relaunch. `runtime.sendNativeMessage` to the host app produced no os_log lines (unverified whether the permission needs re-granting after a manifest change). Still open: everything Windows-specific, `isWindowClosing` accuracy (not needed any more thanks to held closes), and alarm behavior while Safari is closed.


Run each on Safari (macOS, recommended floor and latest) and Brave (Windows), with extension granted all-site access.

1. Does `tabs.move` exist and work in Safari, within and across windows? If not, confirm the fallback.
2. With only `tabs` permission plus the backend host permission, does Safari return `Tab.url` for all http(s) tabs? What does an "Ask" or "Deny" site return, and does `onUpdated` still fire?
3. Does restoring tabs on launch (Safari "reopen windows", Brave "continue where you left off", and "reopen closed window") fire `tabs.onCreated`? Is `url` populated at that moment, and in what order relative to `runtime.onStartup`?
4. `onRemoved.isWindowClosing` accuracy: close one tab vs close window vs quit browser vs last-tab-closes-window, in both browsers. Does quitting emit any events?
5. Safari worker/background lifetime in practice: is it unloaded at ~30 s, does an alarm at 30 s / 5 min wake it, and does the alarm survive a Safari quit and relaunch? Is `onStartup` fired on every launch and is the worker started before the first tab events?
6. Does `onInstalled` fire spuriously on Safari 18.4 to 26.1 (profiles, relaunch)? Confirm idempotent setup.
7. Private windows: with and without the extension enabled for private browsing, do `tabs.query`, `windows.getAll`, `onCreated`, and `onUpdated` expose private tabs in Safari and incognito tabs in Brave? Confirm `incognito` flags, and the Brave "Allow in private" setting (not covered by fetched Chrome docs).
8. Safari 18.4+ `fetch` to the backend: is it blocked until `permissions.request({origins})` is granted, does `optional_host_permissions` suffice, and does the grant persist across Safari restarts? Does the backend need any CORS headers, or only host permission, in each browser? Does HTTPS with a self-signed or private-CA certificate work?
9. `permissions.request` from the popup: is the user-gesture requirement met when the popup closes during the prompt (Safari and Chrome)?
10. `tabs.update({url})` on an existing tab: history preserved on the Safari floor (fixed in 26.0 only)? `tabs.create({pinned:true})` on 18.4+.
11. Detecting human vs extension-initiated change: which of `onUpdated`, `onActivated`, `webNavigation.onCommitted` (Safari lacks `transitionType`) distinguish user actions, and how do we recognise our own writes (and other extensions' changes)? Our plan relies only on URL diffs plus a pending-operation journal.
12. Safari behavior when the user toggles site access or disables the extension while running; how our worker detects lost access (empty URLs) and reports it in the popup.
13. Whether the old name `safari-web-extension-converter` still runs, and what Xcode version the build machine needs (not stated on the fetched Apple pages).
14. Windows-side Brave specifics not covered by sources: Shields/Tor windows treatment of extensions, minimum Windows version for the targeted Chromium.
