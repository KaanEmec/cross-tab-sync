# Synchronization protocol v1

Wire contract between the extensions and the Go service. Breaking changes bump the `/v1` prefix.

## Concepts

| Term | Meaning |
| --- | --- |
| **Device** | One paired browser. Has a UUID, a name, a browser kind, and a bearer token. |
| **Session** | The single shared tab set. Has a `revision`, an `owner`, and a list of entries. |
| **Entry** | One shared tab. `id` is a UUID generated by the device that opened it. Identity of content is the exact `url` string (http/https only, query and fragment preserved). |
| **Revision** | Monotonic integer. Equals the sequence number of the last applied operation. |
| **Owner / generation** | At most one owner device. Every acquisition increments `generation`. Writes carry the generation and are rejected if it is stale. |
| **Operation** | A retry-safe change with a client-generated `opId` (UUID). The server stores the result per `opId` and returns it unchanged on replay. |
| **Tombstone** | A closed entry. Kept so a stale device cannot reopen it from an old snapshot. |

## Authentication

- Every request except `POST /v1/pair` carries `Authorization: Bearer <token>`.
- Tokens are random 32-byte values, base64url-encoded, prefixed `cts_`. The server stores only the SHA-256 hash.
- A revoked device gets `401 device_revoked` and must clear local credentials.
- HTTPS is required unless the server runs with `CTS_ALLOW_INSECURE=1` (local development only).

### Pairing

1. A pairing code is created with the CLI (`cross-tab-sync pair-code`) or by an already paired device (`POST /v1/pairing-codes`). Codes are 8 characters, single use, valid 10 minutes.
2. The new device calls `POST /v1/pair` with `{code, name, browser}` and receives `{deviceId, token}`.

## Session model

```jsonc
{
  "revision": 42,
  "owner": { "deviceId": "…", "name": "MacBook Safari", "generation": 7, "lastSeenAt": "…" } | null,
  "entries": [
    { "id": "…", "url": "https://…", "pinned": false, "position": 0, "updatedRevision": 40 }
  ]
}
```

`entries` contains open entries only, sorted by `position` then `id`. `position` is a best-effort order hint.

## Operations

All operations: `{ "opId": uuid, "type": "...", ...fields }`. Server-side semantics:

| Type | Fields | Effect | Result `status` |
| --- | --- | --- | --- |
| `open` | `entryId`, `url`, `pinned?`, `position?` | If an open entry with the same `url` exists, nothing is created and the result points at it. Otherwise a new entry is created. | `applied` · `coalesced` (`entryId` = existing) |
| `navigate` | `entryId`, `url` | Updates the entry's URL. If another open entry already has `url`, this entry is closed and the result points at the other. If the entry is closed, it is ignored. | `applied` · `coalesced` · `ignored` |
| `close` | `entryId` | Closes the entry (tombstone). Already closed: nothing happens. | `applied` · `ignored` |
| `update` | `entryId`, `pinned?`, `position?` | Updates metadata of an open entry. | `applied` · `ignored` |

Every applied operation (not `ignored`, not a replay) increments `revision` by one. Replays (known `opId`) return the stored result with `replayed: true` and do not change state.

A batch is applied atomically in order inside one transaction. Before a batch that contains `close` or `navigate`, the server stores a recovery snapshot of the open entries.

## Endpoints

| Method and path | Auth | Body | Response |
| --- | --- | --- | --- |
| `GET /healthz` | none | | `200 {"status":"ok"}` |
| `POST /v1/pair` | none | `{code, name, browser}` | `201 {deviceId, token}` · `400 invalid_code` |
| `POST /v1/pairing-codes` | device | | `201 {code, expiresAt}` |
| `GET /v1/devices` | device | | `200 {devices:[{id,name,browser,createdAt,lastSeenAt,isSelf}]}` |
| `DELETE /v1/devices/{id}` | device | | `204` · `404 not_found`. Revoking the owner clears ownership. |
| `GET /v1/session` | device | | `200` session model |
| `GET /v1/session/changes?since=R` | device | | `200 {revision, owner, operations:[{seq, deviceId, op, result}]}` · `410 history_expired` (full resync needed) |
| `POST /v1/session/acquire` | device | `{force?: bool}` | `200 {generation, session}` · `409 owner_active {owner}` |
| `POST /v1/session/release` | device | `{generation}` | `204` · `409 stale_owner {owner}` |
| `POST /v1/session/heartbeat` | device | `{generation}` | `204` · `409 stale_owner {owner}` |
| `POST /v1/session/operations` | device | `{generation, baseRevision, operations:[…]}` | `200 {revision, results:[{opId,status,entryId?,replayed?}], catchUp:{operations:[…]}}` · `409 stale_owner {owner}` |
| `GET /v1/snapshots` | device | | `200 {snapshots:[{id,revision,deviceId,reason,createdAt,entryCount}]}` |
| `POST /v1/snapshots/{id}/restore` | device | `{generation}` | `200 {revision, results}` — restoration is issued as ordinary `open` operations, never a rewind |

### Acquire rules

- Caller is already the owner: returns the current generation unchanged.
- No owner, or the owner's `lastSeenAt` is older than the liveness window (`CTS_OWNER_LIVENESS`, default 10 minutes): ownership moves to the caller, `generation` increments.
- Owner is live and `force` is false: `409 owner_active`. Manual **Continue here** sends `force: true`; automatic takeover (v0.2) does not.
- `heartbeat` and `operations` refresh the owner's `lastSeenAt`. Heartbeats are liveness, never user activity.

### Operations rules

- Rejected entirely with `409 stale_owner` when the caller is not the owner or `generation` is stale. Nothing is applied.
- `baseRevision` is the last revision the client applied. The response's `catchUp` contains operations from other devices after `baseRevision` and before this batch, so the client needs no second request. It does not reject on mismatch; operations are entry-addressed, not positional.
- Limits: 500 operations per batch, 2048-byte URLs, 64 KiB bodies.

## Errors

`{ "error": "snake_case_code", "message": "human readable", ...details }`. Codes: `invalid_request`, `invalid_code`, `unauthorized`, `device_revoked`, `not_found`, `owner_active`, `stale_owner`, `history_expired`, `payload_too_large`, `internal`.

## Client behavior (v0.1 manual handover)

Local persisted state: credentials, server URL, device name, `lastRevision`, `generation` (when owner), `mappings` (`tabId → entryId` plus URL duplicate counts), and a `pending` operation journal.

- **Hand over**: capture eligible tabs → create `open` ops for tabs not mapped to an entry → `POST operations` → apply `catchUp` locally → `release` → status "handed over at revision R".
- **Continue here**: `acquire {force:true}` → for each session entry: reuse an existing eligible local tab with the same URL (map it) or create the tab in the background in the designated window → publish `open` ops for local eligible tabs that are still unmapped → status "owner, generation G, revision R".
- Both actions preserve the active tab and window. Received tabs never steal focus.
- Eligible tabs: `http`/`https` URLs in normal (non-private) windows. Browser pages, private windows and discarded placeholder entries without a URL are excluded.

## Privacy

The server sees URLs, pinned state, order, device names and timestamps; it must, in order to coalesce duplicates. Logs record request method, path, status, device id and latency only. End-to-end encryption is out of scope for v1 (see [ARCHITECTURE.md](ARCHITECTURE.md#key-decisions)).
