# Synchronization protocol v3

Wire contract between the extensions and the Go service. Breaking changes bump the prefix; v3 (many sessions per server) replaced v2; older prefixes answer `404 not_found`. Upgrading to v3 keeps a v2 session that has a key check and an active device; otherwise its data is dropped.

## Concepts

| Term | Meaning |
| --- | --- |
| **Device** | One paired browser in one session. Has a UUID, a name (unique among the session's active devices, ignoring case), a browser kind, and a bearer token. Pairing again creates a new device. |
| **Session** | One shared tab set; a server holds many, each reachable only by its paired devices. Has a `revision`, an `owner`, a key check and a list of entries. |
| **Entry** | One shared tab. `id` is a UUID generated by the device that opened it. Identity of content is the exact URL string (http/https only, query and fragment preserved), which the server sees only as `urlKey` (keyed hash) and `urlEnc` (ciphertext); see Encryption. |
| **Revision** | Monotonic integer. Equals the sequence number of the last applied operation. |
| **Owner / generation** | At most one owner device. Every acquisition increments `generation`. Writes carry the generation and are rejected if it is stale. |
| **Operation** | A retry-safe change with a client-generated `opId` (UUID). The server stores the result per `opId` and returns it unchanged on replay. |
| **Tombstone** | A closed entry. Kept so a stale device cannot reopen it from an old snapshot. |

## Authentication

- Every request except `POST /v3/sessions` and `POST /v3/pair` carries `Authorization: Bearer <token>`. The token maps to a device and the device to its session; no request names a session.
- Tokens are random 32-byte values, base64url-encoded, prefixed `cts_`. The server stores only the SHA-256 hash. A revoked device gets `401 device_revoked`; a device whose session was deleted gets `401 unauthorized`. A paired client treats both the same: clear local credentials and the key, pair again.
- HTTPS is required unless the server runs with `CTS_ALLOW_INSECURE=1` (local development only). The service trusts `X-Forwarded-Proto: https` from the reverse proxy; plain HTTP gets `403 invalid_request`.
- **Rate limit**: `POST /v3/sessions` and `POST /v3/pair` share an in-memory budget of 10 requests per 10 minutes per client IP (the value of the header named by `CTS_CLIENT_IP_HEADER` when set, for example `CF-Connecting-IP` behind Cloudflare; else the last `X-Forwarded-For` entry, which a proxy that replaces the header sets to the connecting client, trusted like `X-Forwarded-Proto`; else the connection address); beyond it they answer `429 rate_limited` with `Retry-After` seconds.

### Sessions and pairing

1. **Start**: the first browser generates the root key and calls `POST /v3/sessions` with `{keyCheck, name, browser}`. The server creates a session with that key check and the browser as its first device, and answers like `pair`. `CTS_MAX_SESSIONS` (default 0 = unlimited; a personal server sets 1) caps sessions per server: `403 sessions_closed`.
2. **Invite**: a paired device creates a code with `POST /v3/pairing-codes`. Codes are 8 characters from `ABCDEFGHJKMNPQRSTUVWXYZ23456789`, single use, valid 10 minutes, and belong to the creator's session (at most 10 live codes per session; a new one replaces the oldest); input is case-insensitive and spaces or dashes are ignored.
3. **Join**: the new device calls `POST /v3/pair` with `{code, name, browser}`, joins the code's session and receives `{deviceId, token, name}`. `name` is 1–64 characters, `browser` 1–32. `CTS_MAX_DEVICES` (default 10) caps active devices per session: `403 session_full`. When another active device of the session already has the name (ignoring case), the server appends the lowest free ` N` (N ≥ 2), e.g. `Brave on macOS 2`, shortening the base so the result stays within 64 characters. Revoked devices do not hold names. The stored name is returned by `sessions`, `pair` and `PATCH /v3/devices/{id}`. Renaming to one's own current name keeps it.
4. **Invite link**: stored server URL, `#`, code, `.`, key: `https://tabs.example.com#ABCD2345.<key>`; `<key>` is the 43-character base64url root key. A link without a key is invalid.

## Session model

```jsonc
{
  "revision": 42,
  "keyCheck": "<43 base64url chars>",
  "owner": { "deviceId": "…", "name": "MacBook Safari", "generation": 7, "lastSeenAt": "…" } | null,
  "entries": [
    { "id": "…", "urlKey": "<43 base64url chars>", "urlEnc": "<base64url ciphertext>", "pinned": false, "position": 0, "updatedRevision": 40 }
  ]
}
```

`entries` contains open entries only, sorted by `position` then `id`. `position` is a best-effort order hint. **Lifetime**: revoking a session's last active device (Disconnect or `DELETE /v3/devices/{id}`) deletes the session and its data at once: nobody could reach it again. The prune job deletes sessions none of whose devices has been seen for `CTS_SESSION_RETENTION` (default `4320h`, 180 days). Browsers keep their tabs; only unreachable server state goes.

## Operations

All operations: `{ "opId": uuid, "type": "...", ...fields }`. Server-side semantics:

| Type | Fields | Effect | Result `status` |
| --- | --- | --- | --- |
| `open` | `entryId`, `urlKey`, `urlEnc`, `pinned?`, `position?` | If an open entry with the same `urlKey` exists, nothing is created and the result points at it. Otherwise a new entry is created; a missing `position` is appended after the highest. Reopening a tombstoned `entryId` is ignored; opening an already open `entryId` coalesces to itself. | `applied` · `coalesced` (`entryId` = existing) · `ignored` |
| `navigate` | `entryId`, `urlKey`, `urlEnc` | Updates the entry's URL fields. If another open entry already has `urlKey`, this entry is closed and the result points at the other. If the entry is closed, it is ignored. | `applied` · `coalesced` · `ignored` |
| `close` | `entryId` | Closes the entry (tombstone). Already closed: nothing happens. | `applied` · `ignored` |
| `update` | `entryId`, `pinned?`, `position?` | Updates metadata of an open entry. | `applied` · `ignored` |

Every `applied` or `coalesced` operation increments `revision` by one; `ignored` operations are stored for replay but never appear in `changes` or `catchUp`. Replays (known `opId`) return the stored result with `replayed: true` and do not change state. `opId` and `entryId` are lowercase canonical UUIDs.

A batch is applied atomically in order inside one transaction. Before a batch that contains `close` or `navigate`, the server stores a recovery snapshot of the open entries.

## Endpoints

Every authenticated endpoint acts only on the caller's session: its devices, pairing codes, entries, operations, revision, generation, owner, snapshots, key check, `minRevision` and history. Ids from another session behave as unknown. Unmatched paths, `/v1` and `/v2` included, answer `404 not_found`.

| Method and path | Auth | Body | Response |
| --- | --- | --- | --- |
| `GET /` | none | | `200` static HTML page (no script): what the server is, install and privacy links, paste invite links into the extension |
| `GET /healthz` | none | | `200 {"status":"ok"}` |
| `POST /v3/sessions` | none | `{keyCheck, name, browser}` | `201 {deviceId, token, name}` · `400 invalid_request` · `403 sessions_closed` · `429 rate_limited` |
| `POST /v3/pair` | none | `{code, name, browser}` | `201 {deviceId, token, name}` · `400 invalid_code` · `403 session_full` · `429 rate_limited` |
| `POST /v3/pairing-codes` | device | | `201 {code, expiresAt}` |
| `GET /v3/devices` | device | | `200 {devices:[{id,name,browser,createdAt,lastSeenAt,isSelf,revokedAt?}]}`: active devices oldest first, then devices revoked within the last 7 days (most recent first) with `revokedAt` |
| `PATCH /v3/devices/{id}` | device | `{name}` | `200 {id,name,browser,createdAt,lastSeenAt,isSelf}` with the stored (possibly suffixed) name · `403 forbidden` when `id` is not the caller · `400 invalid_request` (name 1–64 characters) |
| `DELETE /v3/devices/{id}` | device | | `204` · `404 not_found`. Revoking the owner clears ownership; revoking the last active device deletes the session. |
| `GET /v3/session` | device | | `200` session model |
| `GET /v3/session/changes?since=R` | device | | `200 {revision, owner, operations:[{seq, deviceId, op, result}]}` · `410 history_expired` (full resync needed) |
| `POST /v3/session/acquire` | device | `{force?: bool}` | `200 {generation, session}` · `409 owner_active {owner}` |
| `POST /v3/session/release` | device | `{generation}` | `204` · `409 stale_owner {owner}` |
| `POST /v3/session/heartbeat` | device | `{generation}` | `204` · `409 stale_owner {owner}` |
| `POST /v3/session/operations` | device | `{generation, baseRevision, operations:[…]}` | `200 {revision, results:[{opId,status,entryId?,replayed?}], catchUp:{operations:[…]}}` · `409 stale_owner {owner}` |
| `POST /v3/session/merge` | device | `{operations:[{…, baseRevision}]}` | `200 {revision, results}` — no ownership needed; causal rules below |
| `GET /v3/snapshots` | device | | `200 {snapshots:[{id,revision,deviceId,reason,createdAt,entryCount}]}`. `revision` is the revision just before the change that triggered the snapshot; `reason` is `operations` or `restore`. |
| `POST /v3/snapshots/{id}/restore` | device | `{generation}` | `200 {revision, results}` — restoration is issued as ordinary `open` operations, never a rewind |

### Acquire rules

- Caller is already the owner: returns the current generation unchanged.
- No owner, or the owner's `lastSeenAt` is older than the liveness window (`CTS_OWNER_LIVENESS`, default 10 minutes): ownership moves to the caller, `generation` increments.
- Owner is live and `force` is false: `409 owner_active`. Manual **Continue here** sends `force: true`; automatic takeover (v0.2) does not.
- `heartbeat` and `operations` refresh the owner's `lastSeenAt`. Heartbeats are liveness, never user activity.

### Operations rules

- Rejected entirely with `409 stale_owner` when the caller is not the owner or `generation` is stale. Nothing is applied.
- `baseRevision` is the last revision the client applied. The response's `catchUp` contains operations from other devices after `baseRevision` and before this batch, so the client needs no second request. It does not reject on mismatch; operations are entry-addressed, not positional.
- Limits: 500 operations per batch (`413 payload_too_large`); `urlKey` exactly 43 base64url characters and `urlEnc` 1–4096 base64url characters, checked by a single pass over the bytes, never decoded (`400 invalid_request` for the whole batch); 256 KiB bodies. Clients split batches by encoded size (240 KiB).
- `baseRevision` is required. An empty `operations` array acts as a heartbeat plus catch-up.
- If `baseRevision` is older than the retained history, the response carries `fullResync: true` and no `catchUp`; the client must reload `GET session`.
- `catchUp.operations` and `changes.operations` items are `{seq, deviceId, op, result}` where `op` is the operation as sent and `result` is `{status, entryId?}`.

### Merge rules (offline changes, v1.0)

`POST /v3/session/merge` accepts a journal from any paired device, owner or not, and applies it atomically with per-operation causal checks against each operation's own `baseRevision` (the revision the device had applied when it recorded the change). It never requires ownership and never changes ownership. Results and `revision` behave as for `operations`.

| Operation | Entry unchanged since `baseRevision` | Entry navigated since (or `baseRevision` older than retained history) |
| --- | --- | --- |
| `open` (fresh `entryId`) | applied, coalescing on `urlKey` | applied, coalescing on `urlKey`. Reopening a tombstoned `entryId` stays ignored. |
| `navigate` | applied | converted to `open` of a fresh entry with the new `urlKey`/`urlEnc`, so both divergent destinations survive (`status: "forked"`, result `entryId` = new entry) |
| `close` | applied | ignored: the entry now represents a different page |
| `update` | applied | ignored |

"Navigated since" means another device changed the entry's URL at a revision greater than the operation's `baseRevision`; a device's own earlier changes never make its later operations stale. Metadata-only changes do not block a close. A base ahead of the current revision counts as expired.

- The forked entry id is UUIDv5 with the `opId` as namespace and the name `forked`; it copies the source entry's pinned state and is appended after the highest position. If the forked URL is already open, the result is `coalesced` to that entry.
- Later operations in the same batch that target the forked entry's source are redirected to the fork. Across requests this is not remembered: after a `forked` result the client must rewrite its remaining pending operations for that entry to the new id.
- The log records operations as applied (a forked navigate is logged as an applied `open` of the fork), so `changes` and `catchUp` consumers never see `forked`; only the direct merge response and its replay report `forked`.
- Operations older than the retention window are treated as new if resubmitted, so a resent opening of a pruned closed entry recreates it.
- Operations on closed or unknown entries are `ignored`. Merged operations carry generation 0 and do not refresh the owner's liveness.

### History retention (v1.0)

- The server keeps operations and tombstones for `CTS_HISTORY_RETENTION` (default 30 days) and never prunes below the current open entries. `minRevision` is the oldest retained sequence number; `GET session` and `changes` responses include it.
- `changes?since=R` with `R < minRevision - 1` returns `410 history_expired`. The client reloads `GET session`, reconciles mappings by URL (entries no longer present are detached, never republished), keeps its pending journal, and submits it through `merge`.
- Pruning runs at startup and once per hour. It cuts the log at one sequence number (the first retained operation), so retained history is contiguous.

## Errors

`{ "error": "snake_case_code", "message": "human readable", ...details }`. Every ownership `409` (`owner_active`, `stale_owner`) carries `owner` (possibly `null`); `429` carries a `Retry-After` header. Timestamps are RFC 3339 UTC with milliseconds. Codes: `invalid_request`, `invalid_code`, `unauthorized`, `device_revoked`, `forbidden`, `not_found`, `sessions_closed`, `session_full`, `owner_active`, `stale_owner`, `history_expired`, `payload_too_large`, `rate_limited`, `internal`.

## Client behavior (v0.1 manual handover)

Local persisted state: credentials, server URL, device name, `lastRevision`, `generation` (when owner), `mappings` (`tabId → entryId` plus URL duplicate counts), and a `pending` operation journal.

- **Hand over**: capture eligible tabs → create `open` ops for tabs not mapped to an entry → `POST operations` → apply `catchUp` locally → `release` → status "handed over at revision R".
- **Continue here**: `acquire {force:true}` → for each session entry: reuse an existing eligible local tab with the same URL (map it) or create the tab in the background in the designated window → publish `open` ops for local eligible tabs that are still unmapped → status "owner, generation G, revision R".
- Both actions preserve the active tab and window. Received tabs never steal focus.
- **Hand over** is refused when the device is not the owner. With nothing to publish it only catches up via `changes`.
- All local tabs with the same URL map to one entry; one `open` per distinct URL. A mapped tab keeps its mapping when its URL changes (navigation sync arrives in v0.2). Mappings are cleared on browser startup because tab ids are not stable across restarts.
- Applying `catchUp`: `open` reuses or creates a background tab, `navigate` updates mapped tabs, `close` only unmaps (no local closure in v0.1), `update` applies pinned state. Own operations and `ignored` results are skipped.
- While owner, the worker heartbeats every 5 minutes; `stale_owner` drops owner state but keeps the pending journal.
- **Disconnect** releases ownership if owner, revokes the device itself, then clears credentials.
- Pairing requests the backend origin with `permissions.request` from the popup (user gesture) before calling `/v3/sessions` or `/v3/pair`; the form is persisted first because the prompt may close the popup.
- Eligible tabs: `http`/`https` URLs in normal (non-private) windows. Browser pages, private windows and discarded placeholder entries without a URL are excluded.

## Client behavior (v0.2 automatic sync)

Builds on the v0.1 rules. The server is unchanged: an empty `operations` batch is the owner heartbeat, `acquire {force:true}` is takeover, `changes?since=` is the follower pull.

### Roles and cadence

- A 5-minute `alarms` cycle runs on every device, plus an immediate run after takeover and manual actions. The owner also runs about 2 s after a local change; followers only journal.
- **Owner run**: flush the journal with `POST operations` (empty batch if nothing pending), apply `catchUp`, advance `lastRevision`. `409 stale_owner` drops owner state, keeps the journal, and the device continues as a follower.
- **Follower run**: submit the pending journal through `merge` (v1.0), then `GET changes?since=lastRevision`, apply, advance, and merge again anything the pull produced. Followers never acquire. `410 history_expired` triggers a full resync from `GET session` (reconcile mappings by URL, create missing tabs, never close).
- A persisted run lock makes runs exclusive; a run that finds the lock held exits.

### Recording local changes (both roles, always journaled)

- **Addition**: `tabs.onCreated` or a first eligible URL on `tabs.onUpdated` for a tab the extension did not create. If the URL is already mapped to an entry, the tab becomes another local copy (count +1, no operation). Otherwise `open` with a new `entryId`.
- **Closure**: `tabs.onRemoved` with `isWindowClosing: false` on a mapped tab. Count −1; if it was the last local copy, `close`. Window closure, shutdown, crash, and absence from a capture only unmap. Removals during the first 10 s after startup are treated as unmap only.
- **Navigation**: `tabs.onUpdated` with a new committed URL (status `complete`) on a mapped tab, not caused by remote application. Single local copy: `navigate {entryId, url}`. One of several copies: the tab detaches from its entry (count −1) and is recorded as a fresh `open` for the new URL. Navigating to a URL that is already mapped locally coalesces (the tab joins that entry; the old entry gets `close` if this was its last copy).
- **Echo suppression**: the extension records what it is about to create, navigate, or remove (`expected` set keyed by tab id and URL, with a timeout) and ignores the matching events.
- The journal is sent immediately when owner; followers send it on their next run through `merge`.

### Applying remote operations

- `open`: reuse an eligible local tab with the same URL, else create in the background in the receiving window.
- `navigate`: update every mapped local copy; if the destination is already open locally, the copies are closed (background copies only) and the entry maps to the existing tab.
- `close`: close the mapped background copies. If the active tab is among them, it stays open, is unmapped, and is put in a `detached` set. A detached tab stays local until it moves to a different site or closes: a URL change within the same origin (scheme, host, port), such as a feed rewriting its URL, only updates the detached URL; a different origin is published as a fresh `open`. Materializing (Continue here, Hand over) applies the same rule.
- `update`: apply pinned state; position is a hint only.
- The active tab and focused window never change as a result of application.

### Automatic ownership

- **Activity signals**: `tabs.onActivated` (not for tabs the extension created), `windows.onFocusChanged` to a normal window, and user-created tabs whose URL is eligible (http/https; a new tab page or extension page is not). Navigation and page loads are never activity: restored tabs finish loading long after startup. Signals in the first 30 s after startup (browser start or extension update), restored tabs, and signals caused by remote application are not activity. Heartbeats are never activity.
- **Fresh interaction**: a signal after at least 60 s without signals, or the first signal after this device lost ownership. A browser that merely stays focused produces none.
- **Takeover**: on a fresh interaction while not owner, run Continue here (`acquire {force:true}`, reconcile, flush the journal). At most one attempt per 30 s.
- **Manual Hand over** counts as the latest interaction and suppresses the "ownership lost" rule; only 60 s of quiet followed by a signal takes over again.
- A fresh interaction inside the 30 s rate limit, or a failed takeover, stays pending and fires on the next signal after the limit.
- A freshly paired device (revision 0) rebuilds from the full session instead of replaying history.
- A load the extension started stays its own until 10 s after its first committed event (redirects, post-load URL rewrites); user navigation inside that window is not published.
- A new browser session is detected by a marker in `storage.session` before any event is handled; the startup reset then runs even if the restored tabs' events arrive before `runtime.onStartup`.
- Continue here first applies `changes?since=lastRevision` (410 → full session), then materializes. Materializing navigates mapped tabs whose entry URL moved when nothing local is pending for that entry.
- Divergence: when a remote navigate or close meets a local pending navigate for the same entry, local copies are forked to a fresh entry (`open` of the local URL) and the remote URL gets its own background tab; nothing is overwritten.
- `close` operations are held for 2 s and dropped (unmap only) if the window disappeared, `windows.onRemoved` fired, or a new browser session started. Rapid individual closes (several cmd-W within 2 s) are never dropped as a group: each last-copy removal becomes its own `close`. Removals of copies of one entry are one closure (Safari reports a pinned tab once per window).
- Tabs mapped to entries that are no longer in the session are detached, not republished. Continue here, a full resync and applying a coalesced `open` never recreate entries this device has a pending `close` for, including a removal still held (not yet released or dropped).
- Browsers remove tabs asynchronously: a tab the extension is removing (live `remove` expectation) is left out of every capture (materialize, application, creates) and its events never journal an addition.
- Previous-session mappings and the detached set survive a restart for 60 s so late-restored tabs still match.
- Local pin changes are not published in v0.2.
- The superseded owner learns of the change from `409 stale_owner` on its next run, keeps its journal, and follows; its pending work goes through `merge` on that run. The cadence bounds the window in which the prior owner's unpublished changes are invisible to the new owner.
- A device that believes it is owner verifies ownership at once (no debounce; an empty batch when nothing is pending) on any counted activity signal, at most once per 10 s regardless of the 60 s idle rule (always on a fresh interaction). Window focus alone is not enough: Safari does not reliably report it when the app is activated. The 60 s rule still decides takeovers. When a run demotes the device and the last activity signal is less than 15 s old (not paused), it takes over right after the run, subject to the 30 s limit (a rate-limited takeover stays pending).

## Client behavior (v1.0 offline merging, recovery, controls)

- Every journaled operation stores its own `baseRevision`. `forked` and `coalesced` results move the local tabs to the result entry and rewrite remaining pending operations for the old entry. `ignored` navigates are re-recorded as a fresh `open` of the local URL so a following remote `close` cannot shut the user's page; other `ignored` results are dropped.
- Network errors and 5xx responses set `online: false` and schedule a retry with exponential backoff (30 s doubling to a 5-minute cap, reset on success). Alarm and debounced runs wait for the retry time; Sync now, Resume and automatic takeover do not.
- `fullResync` on `operations` and `410` on `changes`: reload `GET session`, re-match mappings by URL, unlink tabs of vanished entries (never close), keep the journal, send the remainder through `merge`. Journals written before v1.0 carry `baseRevision: 0`.
- The popup distinguishes "Saved to server" (acknowledged) from application on other devices, shows pending counts and the retry time while offline, and gives one actionable message per error class: unauthorized, revoked, missing site permission (with a Grant access button), unreachable, server error.
- **Pause** stops runs and automatic takeover; journaling continues; manual actions are refused. **Resume** releases held closes (dropped if their window is gone), then runs.
- **Restore**: take over if not owner (catch up if owner), `POST /v3/snapshots/{id}/restore` with the current generation, then rebuild from `GET session` so restored tabs open in the background. Restore reopens URLs only.
- **Devices**: the popup lists devices (this device marked, short id = first 8 characters of the device id, last seen) and can revoke another active device; the local device uses Disconnect. Devices revoked in the last 7 days are shown greyed as revoked, without Revoke.
- **Pairing (popup)**: **Start syncing** creates a session on the default server (`https://cts.kexperiments.com`) or the Advanced server URL, then shows Devices with an invite; **I have an invite link** takes a `#CODE.KEY` link. The device name is prefilled as `<Browser> on <OS>`, editable, and stored as the server returns it. `404` on `/v3` reports an older server.
- **Invite another browser** creates a code and shows its link (stored server URL + `#` + code + `.` + key) with a Copy button and the expiry time.
- **This device** shows name (Rename: `PATCH /v3/devices/{id}`), browser, short id (Copy copies the full id), server URL and paired since (backfilled from the device list's `createdAt` for devices paired before it was recorded). The owner line reads `Name (shortid)`.
- `onInstalled` with reason `update` runs the browser-startup reset and immediately re-matches open tabs by URL.

## Encryption

URLs are end-to-end encrypted; the server is blind. Clients derive everything from a 256-bit root key `K` that the first browser generates (`crypto.getRandomValues`) and that travels only inside invite-link fragments, never in a request.

- `HKDF-SHA256(K, salt = empty, info = "cts-url-mac")` → `K_mac`; `info = "cts-url-enc"` → `K_enc` (32 bytes each).
- `urlKey = base64url(HMAC-SHA256(K_mac, url))`, 43 characters, deterministic: the server coalesces duplicates on it.
- `urlEnc = base64url(0x01 ‖ nonce (12 random bytes) ‖ AES-256-GCM(K_enc, nonce, pad(url), aad = urlKey))`. `pad(url)` is a 2-byte big-endian length, the UTF-8 URL, then zero bytes up to a multiple of 64 bytes, so exact lengths are hidden. The leading byte is the format version. The AAD is `urlKey` (not the entry id) because restore and merge forks copy the URL fields to a fresh entry. A 2048-byte URL yields at most 2856 characters.
- **Key check**: `keyCheck = base64url(HMAC-SHA256(K_mac, "cts-key-check"))`. The first browser sends it with `POST /v3/sessions`; every browser compares its own value with the session's `keyCheck` before it sends or applies anything, and keeps a local `keyVerified` flag. A browser whose value differs revokes itself, clears its credentials and key, and reports `key_mismatch`.
- Any authentication failure on decrypt means a different key: the client reports `key_mismatch`, takes no local action, stops automatic runs and takeovers until the browser is paired again, and never moves ownership (Continue here decrypts `GET session` before `acquire`).
- On the wire, `open` and `navigate` must carry `urlKey` and `urlEnc`; the client rejects any received operation that carries a plaintext `url` or lacks the two fields, and after decrypting it recomputes the HMAC of the URL and requires it to equal `urlKey`. The server rejects operations with unknown fields.
- Invite links are built by the browser from its stored server URL and are meant to be pasted into the extension, not opened: a page at the link's origin could read the fragment (the server's root page has no script). Tabs on the server's own origin are not eligible for sync. The client stores the key with the credentials, shows it only inside invite links and clears it on Disconnect.

## Privacy

What the server learns and can still do is the threat model in [ARCHITECTURE.md](ARCHITECTURE.md#threat-model); it does no cryptography, only checks the two URL fields' length and alphabet, stores them verbatim and indexes `urlKey`. The server stores and sees only `urlKey` and `urlEnc` for each tab, plus pinned state, order, device names, revisions and timestamps. Logs record request method, route pattern, status, device id and latency only; the optional diagnostics trace masks anything URL-shaped. Client IPs live only in the rate limiter's memory, at most 10 minutes. Backups of the database contain no readable URLs.
